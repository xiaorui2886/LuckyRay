# 插件目录提交、审核与撤下

目前 `entries.json` 的生产插件列表为空。`examples/` 是官方教学条目，不应作为第三方插件已审核或可直接生产使用的证明。

## 通过 GitHub PR 提交

1. Fork 本仓库，新建分支。将独立条目写入 `catalog/plugins/<插件id>.json`，条目须符合 `schema.json`，首次提交使用 `status: submitted`；本轮只接受 LuckyRay API1 桌面脚本。
2. 填写实际插件 ID、名称、准确 `x.y.z` 版本、作者和公开来源；指向固定版本的源代码/原始制品，不填 `latest` 或会悄然改变的下载链接。没有源码时声明 `sourceAvailable: false`，不能伪装 MIT/开源；许可仍须可核实并允许拟议分发方式。
3. 提供完整许可文件的公开位置和必要版权/NOTICE。注明制品字节数、SHA-256、最低宿主声明、SDK/API 版本和实测宿主版本。来源、作者及许可必须与实际文件相符。
4. 权限逐项对应插件包：必需、可选、用途、本次对象范围、会产生的写入及删除/迁移影响。列出 DSH、外部服务或其他独立依赖；不能要求把凭据放入目录。
5. 附可复现的 CLI check/pack 结果；生产申请另附准确正式宿主上的手动安装、授权、只读、拒绝越权、显式写入及停用/卸载检查结果。只做 CLI 检查时如实写 `authoring-only`，不得填写未经测试的宿主版本。
6. 提交 PR，说明新增/更新原因、验证范围与未验证项。新增权限、作者/来源转移、许可或制品内容改变需要重新审核；同一 ID 改内容必须升级版本。维护者审核通过后，才会改为 `community-reviewed` 并加入生产索引。

## 审核标准

- 来源可追溯：来源和制品版本固定，作者/发布权限可核实，逐项哈希相符。
- 权利完整：保留原许可与第三方声明，核查再分发条件、对应源码或适用提供方式；仅写 SPDX 或“免费”不够。
- 能力诚实：与正式宿主契约相符，不用开发预览新增 API 充当旧宿主能力，不把 CLI 通过当实机验收。
- 权限最小：所有权限有理由，读取和写入区分，尊重本次范围、revision、确认及资源限额；没有官方白名单绕过。
- 内容可审查：不得包含密钥、Cookie、私人路径、真实数据库/笔记、未经授权的记录或素材。教学示例与生产条目清楚区分。
- 用户可理解：说明费用、联网/独立依赖、已知限制和数据影响，提供可公开使用的问题报告入口。

合并目录 PR 是对提交材料的有限审核，不是所有设备上的兼容性测试或绝对安全保证；不会自动在用户电脑上安装或更新插件。

## 报告问题与撤下

普通故障、失效链接、作者/来源或许可争议可开本仓库 Issue，写插件 ID、版本和可公开的证据，并附对应来源；不要复制私密资料。漏洞遵循 [SECURITY.md](../SECURITY.md)，不在公开 Issue 放利用细节。私密入口开放前，请保留敏感报告，不公开细节。

维护者可暂停索引条目、在条目中标记撤下原因并通过 PR 留下必要的公开变更说明。对个人数据泄露，应先停止继续展示泄露内容，再处理后续记录；不要在说明中再次复制秘密。作者可以通过 PR/Issue 请求撤下并提供权属依据。

撤下目录条目不能从用户电脑远程删除插件，也不会自动撤销已安装版本或清理用户笔记。用户应在软件内停用/卸载，并按插件说明处理自有数据、生成文件与相关授权。
